# EXPLANATION.md — CSRF where token is tied to non-session cookie

## Модель защиты

Сервер сверяет CSRF-токен из тела запроса не с сессией, а с отдельной кукой `csrfKey`.
Изъян: кука не привязана к сессии — выдаётся любому посетителю, при перелогине не меняется.
Сервер принимает **любую согласованную пару** `csrf` + `csrfKey`, лишь бы значения совпадали.

Следствие: атакующему достаточно доставить жертве **свою пару** — токен (легко, это поле формы)
и куку (сложно, это заголовок).

## Почему куку нельзя установить напрямую

Куку браузеру устанавливает только **сервер целевого домена**:

- `document.cookie` со страницы exploit-домена пишет куки exploit-домена (Same-Origin Policy),
  а не домена лабы;
- XHR/fetch не помогут: `Cookie` — forbidden header name, браузер игнорирует его установку.

Остаётся канал «сервер лабы сам отправит нужный `Set-Cookie`» — для этого нужен примитив,
управляющий заголовками ответа.

## Примитив: CRLF-инъекция

Если пользовательский ввод попадает в заголовок ответа без санитизации, `%0d%0a`
(CRLF — разделитель заголовков HTTP) завершает текущий заголовок, а всё, что после,
сервер отдаёт как **новый заголовок, контролируемый атакующим**:

```
GET /?search=test%0d%0aSet-Cookie:%20csrfKey=<KEY>;%20SameSite=None

Set-Cookie: LastSearchTerm=test
Set-Cookie: csrfKey=<KEY>; SameSite=None; Secure; HttpOnly
```

`Secure` и `HttpOnly` не препятствуют: куке не нужно читаться из JS — она записывается
и автоматически отправляется браузером.

## Роль SameSite

Куки по умолчанию `SameSite=Lax`: отправляются только в top-level GET-навигации.
Финальный удар атаки — кросс-сайтовый POST с exploit-домена: с `Lax` браузер не приложил бы
куки вообще (ни подменённый `csrfKey`, ни `session` жертвы). Поэтому в инъекции задан
`SameSite=None` — явное разрешение кросс-сайтовой отправки.

## Цепочка атаки (в браузере жертвы)

1. Кросс-доменный GET на URL с инъекцией (например, через `<img>`) → сервер лабы
   устанавливает жертве `csrfKey` атакующего.
2. Сабмит формы POST с телом: `csrf` атакующего + новый email. Браузер сам приклеивает
   куки: `session` жертвы + `csrfKey` атакующего.
3. Сервер: `csrf == csrfKey` → допуск → смена почты под сессией жертвы.

Атака выполняется вслепую: значения кук жертвы атакующий ни разу не видит.

## Почему сработало: композиция слабостей

1. Токен сверяется с не-сессионной кукой → принимается любая согласованная пара.
2. CRLF-инъекция → контроль над заголовками ответа → произвольная кука жертве.

По отдельности — приемлемые практики; вместе — полный обход CSRF-защиты.
Защита не сильнее самого слабого звена системы вокруг неё.

## Переносимые выводы (чек-лист для аналогичных лаб)

1. Определить, с чем сверяется CSRF-токен: сессия / отдельная кука / серверное состояние.
2. Если пара «токен + ключ» — проверить, выдается ли ключ без привязки к сессии.
3. Искать примитив установки кук: отражение ввода в заголовках, CRLF, cookie-shielding
   через субдомены.
4. Проверять SameSite у целевых кук; нужный флаг задавать той же инъекцией.
5. Порядок действий на exploit-странице: сначала установка куки, затем сабмит формы.
