## TL;DR

Правило стенда перестало объясняться сравнением запросов, потому что телеметрия
клиента перекодируется самодельным LCG-потоком, чей ключ зависит от состояния
сессии (mode / nonce-зерно / счётчик / crc32-ratchet). Код клиента лежит в самом
дампе: проигрываем его state-машину, инвертируем `pack()` — и сигнатура
оказывается XOR'ом блоков 1–2 телеметрии, одинаковым у всех сработок.
Фикс для стенда: детект по декодированной телеметрии, а не по wire-байтам.
Флаг: `flag{state_tcp3}`.

## Recon

- `note.txt`: клиент 10.8.0.50, сервер 10.8.0.1:80; событие = (клиентский порт,
  X-Request-ID); списки сработок (d10/d11 × 3 порта) и пропусков (d00–d09 × 3);
  инструкция по флагу.
- `traffic.pcap`: 4 соединения — порт 52990 отдал `GET /assets/probe-session.r9.js`
  (код клиента, ревизия 9), порты 53011/53021/53031 — сессии телеметрии
  (`/open`, `/gate/v3`, `/switch`, `/poll`, `/reset`).
  Проверял: можно ли матчить тела «в лоб» — нет: 64 байта base64 у каждого
  события разные без видимых общих кусков.
  Зацепка: состояния меняются заголовками `x-commit` / `x-ratchet` и статусами
  (409/202/204/208) — то есть ключ потока восстанавливается из трафика.

## Steps

### 1. Собрать HTTP-обмены из дампа

Пересобираю TCP-потоки (ретрансмиссии — поздний пакет побеждает), делю на обмены
по `Content-Length` (код: §1–2 `solve.py`). Дедуп по (порт, X-Request-ID):
повторные d04 и d07 (второй раз `208 Already Reported`) дают те же тела —
это те же измерения, не новые. Итого 36 событий = 3 порта x d00–d11.

Реальный обмен (порт 53011):

```http
POST /gate/v3 HTTP/1.1
Host: gate.filter.local
X-Request-ID: d10
X-Probe-Client: /assets/probe-session.r9.js
Content-Length: 64
Connection: keep-alive

PuapjIqQHrjIpA+LZiVEXH0qGbBTKFxg/xIk9zF0SHNsh4tTZQ5fOuFxScSG4Yx8
```

```http
HTTP/1.1 204 No Content
x-receipt: d10
x-ratchet: 1178edb3
content-length: 0
```

### 2. Понять упаковку (код клиента из дампа)

Тело события — base64 от 48 байт: три блока по 16, переставленных по
`WIRE[mode]`, с сдвигом внутри блока и XOR от байта LCG-потока:

```js
out[16*slot+i] = raw[16*cfg.order[slot] + ((i+shift)&15)] ^ (x>>>24) ^ cfg.salt[slot];
```

Состояние сессии меняет только ответы (логика `onExchange`):

- `/open`, `/reset` (201) → `mode`, `seed = nonce`, `seq = 0`;
- `/switch` → предложение в `pending`; коммит при `x-commit` на любом ответе:
  `mode = p.mode`, `seed = rol(seed ^ salt, 11)`; `409` отменяет;
- `/gate/v3` (204 + `x-receipt`, событие не повторное) →
  `seed = rol(seed ^ crc32(ТЕЛО ЗАПРОСА) ^ x-ratchet, 7) + 0x6d2b79f5`, `seq++`.

Ловушка: crc32 считается по раскодированному телу **запроса** (переменная
`body` в `onExchange`), а не по пустому ответу. Сверил проигрывание с
исполнением настоящего JS в Node — состояния совпали байт-в-байт.

### 3. Проиграть сессию и раскодировать 36 событий

```bash
$ pip install scapy
$ python3 solve.py traffic.pcap note.txt
```

Результат:

```

[+] состояние сессии (порт, id, mode, seed, seq):
    53011 d00 mode=1 seed=f7ea26ee seq=0
    53011 d01 mode=1 seed=4f4e2be6 seq=1
    53011 d02 mode=1 seed=bf3f5931 seq=2
    53011 d03 mode=1 seed=0f81758c seq=3

```

Режимы: 1 (d00–d03) → 3 (d04) → 2 (d05–d06) → сброс 1 (d07–d08) → 3 (d09–d11).

### 4. Найти сигнатуру: 16 байт, общие для сработок

Ни одно 16-байтовое окно не совпадает у сработок — сигнатура «размыта»:
XOR блоков 1 и 2 телеметрии (маска в блоке 2, сигнатура в блоке 1).
`b1^b2` у всех шести сработок одинаков, у пропусков — разный, и ни одно
окно пропусков его не содержит:

```
hit  53011/d10: 24602d333832372e27273121310c2436
hit  53021/d10: 24602d333832372e27273121310c2436
hit  53031/d10: 24602d333832372e27273121310c2436
hit  53011/d11: 24602d333832372e27273121310c2436
hit  53021/d11: 24602d333832372e27273121310c2436
hit  53031/d11: 24602d333832372e27273121310c2436
signature absent from all 30 misses: True
```

### 5. Флаг по инструкции записки

```
[+] сигнатура: 24602d333832372e27273121310c2436
[+] XOR с ключом TSPU: b'p3}flag{state_tc'  ->  перенос 3 байт в конец
FLAG: flag{state_tcp3}
```

## Why it works

Чему доверял стенд: байты запроса однозначно отражают содержание события.
Клиент r9 это ломает: keystream привязан к `seed/seq`, поэтому каждое
событие (даже с одинаковым содержанием) даёт уникальные wire-байты —
сигнатурный матчинг слепнет. Но класс bypass'а здесь «self-defeating
obfuscation»: всё, что определяет keystream, наблюдаемо — nonce в ответах,
`x-ratchet` в заголовках, статусы, `crc32` (не MAC) по видимым данным,
код клиента отгружается браузеру и попал в дамп (Kerckhoffs: обфускация
без секрета на стороне аналитика — не секрет). Проигрывание сессии
восстанавливает полный ключ, инверсия `pack()` возвращает содержание.
Дедупликация по (порт, X-Request-ID) важна: она держит `seq` честным,
иначе все последующие события раскодируются мусором.

## Defense

1. Канонизация перед матчингом: детект по декодированной телеметрии
   с пиннингом версии клиента (расшифровка в аналитическом конвейере),
   а не по wire-байтам.
2. Стандартная крипто вместо самоделки: TLS + AEAD/HMAC; 32-битный LCG
   и crc32 — предсказуемы и подделываемы, это обфускация, а не защита.
3. Серверные идентификаторы и дедуп-ключи событий (не клиентские
   порт+ID), чтобы учёт повторов нельзя было сбить ре-доставкой.
