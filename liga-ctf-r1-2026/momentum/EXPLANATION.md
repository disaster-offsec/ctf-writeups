# Momentum: теория

Класс в задаче один — **boolean-based blind SQLi**. Второй класс (race condition на
балансе) исследован и оказался тупиковым — короткий блок в конце.

## What is it

Blind SQLi — SQL-инъекция, при которой ответ приложения не показывает ни данных, ни
ошибок БД, но меняет наблюдаемое поведение в зависимости от истинности
подставленного условия. Каждый запрос отвечает ровно на один вопрос «да/нет», а
последовательность таких вопросов (бинарный поиск по коду символа) позволяет
выкачать из базы любые строки. В Momentum каналом служит JSON-поле `available`
у публичной проверки промокода: обычная «валидация формы» оказалась
однобитовым интерфейсом чтения ко всей базе.

## How it works

Атака возможна, когда приложение доверяет вводу как части кода запроса и отдаёт
наблюдаемый признак, зависящий от результата SQL. В Momentum приложение доверяло
тому, что:

1. `code` — это строка-данные, которую можно склеить с текстом запроса:
   `SELECT 1 FROM promos WHERE code = '<code>' AND uses_left > 0`. Кавычка во вводе
   закрывает литерал — дальше выполняется SQL атакующего, а хвост запроса съедается
   комментарием `--` (запрос однострочный).
2. Одним битом результата можно отвечать на публичном эндпоинте без ограничений
   частоты: «есть живой код / нет».
3. Движок (SQLite) разрешает подзапросы и функции в WHERE: `length`, `substr`,
   `unicode`, `group_concat`, свободное чтение `sqlite_master`.

Уязвимый запрос (в каноничном примере — POST, здесь GET, остальное то же):

```http
GET /api/v1/promo/check?code=x'+OR+'1'%3D'1'+--+ HTTP/1.1
Host: <instance>
```

SQL, который из него собирает сервер:

```sql
SELECT 1 FROM promos WHERE code = 'x' OR '1'='1' --' AND uses_left > 0
```

`available = (нашли строку)` → true для любого ввода, пока условие атакующего всегда
истинно. Контроль `x' OR '1'='2'--` возвращает false — разница этих двух ответов и
есть оракул.

## Impact

- Что получает атакующий в худшем случае: чтение любой строки из БД, до которой
  дотягивается уязвимый запрос — схема (`sqlite_master`), данные, секреты
  (промокоды, токены, хэши). В Momentum: живой промокод → деньги на балансе → флаг.
- Цепочки: `OR '1'='1'` в логине = auth bypass; если булевого признака в ответе нет,
  оракул переносится во время ответа (time-based) — тот же дамп; на других СУБД класс
  доходит до RCE (MSSQL `xp_cmdshell`, PostgreSQL `COPY ... PROGRAM`) и чтения файлов
  (MySQL `LOAD_FILE`). С race condition на балансе комбинируется естественно, но в
  Momentum гонка не даёт выигрыша (см. блок ниже).

## Defenses

1. Основная защита — **параметризация (prepared statements)**: значение едет по
   проводу отдельно от SQL-текста и никогда не парсится как код, поэтому инъекция
   невозможна по построению:
   `cur.execute("SELECT 1 FROM promos WHERE code=? AND uses_left>0", (code,))`.
2. Вторая линия — allow-list валидация формата до SQL (`^[A-Z0-9]{10}$`), rate limit
   на оракул-эндпоинт, единый ответ для «не найден»/«исчерпан». Это не чинит
   инъекцию, а удорожает эксплуатацию: посимвольный дамп требует сотен–тысяч запросов,
   и каждое ограничение режет их поток.
3. По умолчанию в современных фреймворках: ORM (Django, SQLAlchemy, Prisma) и
   драйверы (python `sqlite3`, `psycopg`, `mysql2`) параметризуют запросы сами.
   Уязвимость появляется там, где разработчик уходит в raw-строки и f-конкатенацию.

## Why defenses break

Классы bypass'ов — скелет задач этой категории:

- bypass 1: «сырые» фрагменты поверх ORM — `.raw()`, `$where`, f-строки внутри
  `execute(...)`, конкатенация «проверенных» кусков. ORM защищает только пока запрос
  параметризован; один raw-фрагмент возвращает уязвимость.
- bypass 2: WAF и чёрные списки режут сигнатуры `OR '1'='1'`, но булев предикат
  выписывается без них: `CASE WHEN`, `LIKE`, конкатенация `||`, комментарии `/**/`,
  кодирование символов; а при отсутствии бита в теле ответа — во времени ответа
  (time-based), где WAF смотреть не на что.
- bypass 3: rate limit и валидация формата стоят на одном эндпоинте, а уязвимый —
  соседний (в Momentum `check` и `redeem` принимают один параметр); клиентский
  debounce/валидация в JS серверным кодом вообще не исполняются.

## Класс 2: race condition (LWW) — исследован, не эксплойтится

- Что проверялось: параллельные `POST /trade` при read-modify-write баланса без
  транзакции — «стакаются» ли выигрыши.
- Как устроено: два запроса читают один баланс, оба выигрывают, каждый пишет свой
  `balance + win`; последний коммит затирает предыдущий (last-write-wins).
- Результат измерений: парные спины k=2 при двойном выигрыше дали баланс одного
  выигрыша (19 500 копеек, а не 39 000) — гонка не ускоряет добычу, торговля только
  серийная.
