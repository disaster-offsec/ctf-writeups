## What is it

Класс: **«удаление улик при живом хэндле»**. Программа пытается «заметать
следы» — удаляет файл с секретом, — но делает это, *пока файл открыт в
памяти*. Windows в такой ситуации удаляет только имя файла, а содержимое
остаётся в памяти до закрытия. Любой дамп процесса за это время возвращает
секрет целиком.

В задаче этот трюк усилен двумя привычками:

- **конфиг в командной строке** — ключ и смещения передаются через argv,
  а командная строка навсегда оседает в памяти процесса, логах и дампах;
- **приманки в памяти** — сотни сгенерированных фейков (`flag{decoy-…}`),
  ломающих поиск по подстроке `strings`/grep.

По сути это не «уязвимость ввода», как в вебе, а ошибка жизненного цикла
секрета: и данные, и «инструкция к ним» переживают все шаги сокрытия.

## How it works

Атака (в нашем случае — сам процесс, а «атакующий» — аналитик) возможна,
пока приложение верит в три вещи:

1. **«Удалил файл — улики нет».** `DeleteFileW` убирает только запись в
   каталоге NTFS. Если на файл есть открытый хэндл или маппинг, содержимое
   живёт в памяти системы до закрытия последнего.
2. **«Секрета в памяти нет, если нет строки»**. Недостаточно не превращать
   секрет в текст: сырые байты всё равно лежат в страницах отображённого
   файла, и полный дамп их захватывает.
3. **«Приманки замаскируют сигнал»**. Фейки мешают поиску по слову, но не
   поиску по *зашифрованному* префиксу, если ключ известен (а он в argv).

Уязвимая последовательность (в шаблоне пример — HTTP-запрос, тут вместо него
WinAPI; комментарии по-человечески):

```c
hFile = CreateFileW(path, GENERIC_READ, FILE_SHARE_READ|WRITE|DELETE,
                    NULL, OPEN_EXISTING, FILE_ATTRIBUTE_NORMAL, NULL);
hMap  = CreateFileMappingW(hFile, NULL, PAGE_READONLY, 0, 0, NULL);
view  = MapViewOfFile(hMap, FILE_MAP_READ, 0, 0, 0);
DeleteFileW(path);      // «улика удалена» — но view ещё жив!
// ... держать 90 секунд, читать байты, плодить приманки ...
// данные исчезнут только здесь:
UnmapViewOfFile(view); CloseHandle(hMap); CloseHandle(hFile);
```

Если между `CreateFileMappingW` и `UnmapViewOfFile` снять полный дамп
(`MiniDumpWriteDump` с `MiniDumpWithFullMemory`) — в файл дампа уходят и
страницы «удалённого» файла, и командная строка процесса, и куча с приманками.

## Impact

- Форензик (или атакующий) получает **полное содержимое «удалённого» файла**
  из одного дампа: не спасают ни удаление файла, ни шифрование диска, ни
  перезагрузка — лишь бы дамп сняли в окне удержания.
- Цепочки с другими классами: (1) дампы/отладка → восстановление секретов,
  которые приложение «убрало»; (2) логирование cmdline (Sysmon, WMI, EDR) →
  раскрытие ключей расшифровки; (3) генерация мусора в памяти → усложнение
  автоматического анализа, но не ручного.

## Defenses

1. **Основная — правильный порядок работы с секретом**: закрыть маппинг и
   хэндл (`UnmapViewOfFile` + `CloseHandle`) *до* удаления файла; после
   чтения — обнулять память (`RtlZeroMemory`); не держать секретный маппинг
   дольше необходимого. Тогда удаление файла действительно удаляет данные.
2. **Вторая линия — не светить конфигурацию**: ключи и смещения передавать
   не через argv (конфиг-файл, DPAPI), а из секрета не делать отладочных
   строк — командная строка всегда попадает в дампы и логи.
3. **Что дано по умолчанию**: NTFS удаляет имя сразу, а данные — с
   последним хэндлом (`FILE_FLAG_DELETE_ON_CLOSE` делает это явным); EDR при
   инциденте снимает дамп, пока процесс жив, — и mapped pages в нём есть.

## Why defenses break

Скелет bypass'ов этой категории:

- **bypass 1**: «файл удалён → данных нет» не покрывает случай открытого
  маппинга: имя и содержимое — независимые вещи, содержимое держит
  ref-count хэндлов.
- **bypass 2**: «секрета нет в строках» не покрывает сырые байты: XOR с
  ключом, лежащим в командной строке того же процесса, снимается одним
  сканом памяти.
- **bypass 3**: «приманки + мусор в куче» не покрывают зашифрованный
  префикс: настоящих вхождений ровно одно, фейков — сотни; ключ отсекает шум.
