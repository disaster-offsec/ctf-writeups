В задаче SolarCTF «Последнее дело» даны отчёт PDF и неизвестная программа. Флаг спрятан в выборе отдельных слов отчёта: нейросеть предлагает восемь замен, программа переставляет их, а позиция фактически использованного слова кодирует три бита.

Флаг:

```text
SOLARCTF{s0l4r_4ray_ds3c_r3s34rch}
```

# Что было в архиве

| Файл | Назначение |
| - | - |
| `report.pdf` | Отчёт на 65 страницах с изменёнными словами |
| `solar.exe` | Windows PE64, программа на Haskell/GHC |
| `solar.s4r` | Упакованные модель и словарь |
| `onnxruntime.dll` | Библиотека для выполнения ONNX-модели |

Связка ONNX Runtime, большого файла ресурсов и текстового отчёта наводит на гипотезу о нейросетевой текстовой стеганографии. Дальнейший разбор подтверждает её: программа использует masked language model, которая оценивает возможные слова вместо `[MASK]`.

Решение состоит из трёх частей: восстановить модель и правила выбора кандидатов, найти заменённые слова в PDF и превратить их позиции в поток битов.

# Распаковка solar.s4r

Первые восемь байт файла — сигнатура `S4R2\r\n\x1a\n`. Далее идут шесть 64-битных чисел в big-endian. Общий размер заголовка — 56 байт.

| Поле | Значение |
| - | - |
| Размер распакованной модели | 29 660 324 |
| Размер упакованной модели | 18 861 790 |
| Размер распакованного словаря | 1 080 667 |
| Размер упакованного словаря | 377 097 |
| FNV-1a-64 модели | `b6e5d5a1a7dcdbd2` |
| FNV-1a-64 словаря | `1898864edc83f4b7` |

За заголовком расположены два потока. Чтобы получить данные, сначала снимаем XOR с потоком xorshift64\*, затем распаковываем zlib. Для модели и словаря генератор инициализируется отдельно:

```python
MODEL_SEED = 0xfc198e053ad614aa
VOCAB_SEED = 0x7ca1a775ec796310
MASK64 = (1 << 64) - 1

def decrypt(packed, state):
    out = bytearray(packed)
    for offset in range(0, len(out), 8):
        state ^= state >> 12
        state ^= (state << 25) & MASK64
        state ^= state >> 27
        key = ((state * 0x2545f4914f6cdd1d) & MASK64)
        key = key.to_bytes(8, 'little')
        for j in range(min(8, len(out) - offset)):
            out[offset + j] ^= key[j]
    return bytes(out)

# raw = zlib.decompress(decrypt(packed, seed))
```

После распаковки проверяем длины и FNV-1a-64 из заголовка. Это даёт `model.onnx` и `vocab.txt` с 83 828 токенами. Начало словаря:

```text
0  [PAD]
1  [UNK]
2  [CLS]
3  [SEP]
4  [MASK]
```

# Поиск слов в PDF

На вид PDF похож на обычный технический отчёт о HardBit. Следы замен обнаруживаются в потоках содержимого страниц, в операторах вывода текста `TJ`.

Обычные слова часто разбиты на фрагменты с привычными поправками кернинга. Некоторые заменённые слова записаны целиком, а соседние интервалы отличаются числом десятичных знаков. Это полезный признак для отбора кандидатов, но не строгий критерий: встречаются и очень маленькие, и целочисленные изменения интервалов.

Поэтому поиск по необычной точности чисел служит начальной эвристикой. Затем нужно проверить контекст, позицию слова и возможность получить его среди кандидатов модели. В результате восстановлено 107 слов-носителей.

Первый контекст выглядит так:

```text
В Solar 4RAYS (ex Solar JSOC CERT) [MASK] заказчик, который был атакован шифровальщиком Hardbit 3.0.
```

В PDF на месте маски стоит `появился`.

Порядок носителей определяется порядком текста в content stream. Он может отличаться от визуального порядка чтения страницы. При извлечении текста обычной утилитой этот порядок легко потерять.

Не менее важны границы предложений и пробелы после склейки строк. В этой задаче пришлось сохранить, в частности, `Form. MaximizeBox` и `<HardBit- TOX-id>` с пробелами. Если в предложении несколько одинаковых слов, маску нужно поставить на конкретное изменённое вхождение.

В `observations.json` сохранены восстановленные предложения, слова и их порядок. Это результат анализа PDF. Приложенный скрипт использует эту разметку; автоматического восстановления разметки из произвольного PDF в нём нет.

# Восстановление кандидатов модели

Предложение с маской сначала нормализуется:

```python
sentence = ' '.join(sentence.split())
```

После этого применяется WordPiece. Базовое разбиение соответствует регулярному выражению:

```python
r'\[MASK\]|[^\W_]+|_|[^\w\s]'
```

Подчёркивание выделяется в отдельный токен. Регистр сохраняется. Каждый фрагмент разбивается жадно по словарю; у продолжений используется префикс `##`. В начало последовательности добавляется `[CLS]`, в конец — `[SEP]`.

ONNX-модель получает четыре входа типа `int64`:

| Вход | Содержимое |
| - | - |
| `input_ids` | Идентификаторы токенов |
| `attention_mask` | Единицы для всех переданных токенов |
| `token_type_ids` | Нули |
| `mask_positions` | Позиция токена `[MASK]` |

Модель возвращает оценки для всех 83 828 токенов. Из них выбираются восемь кандидатов:

1. Сортируем токены по убыванию оценки.

2. Оставляем слова, состоящие только из букв.

3. Удаляем дубликаты без учёта регистра, сохраняя первый вариант.

4. Берём первые восемь оставшихся слов.

```python
candidates = []
seen = set()

for word, score, token_id in predictions:
    folded = word.casefold()
    if word.isalpha() and folded not in seen:
        seen.add(folded)
        candidates.append((word, token_id))
    if len(candidates) == 8:
        break
```

Удаление дубликатов существенно: пары вроде `What`/`what`, `Data`/`data` не должны занимать два места. При этом запрещать заглавные буквы нельзя — регистр выбранного слова сохраняется.

# Перестановка восьми слов

Индекс слова в списке по вероятности ещё не является сообщением. Программа сначала переставляет кандидатов с помощью встроенной виртуальной машины.

Перестановка зависит от контекста. Ключ контекста — FNV-1a-64 от UTF-8 строки следующего вида:

```text
нормализованное_предложение<TAB>id0,id1,id2,id3,id4,id5,id6,id7
```

Идентификаторы записываются десятичными числами в порядке кандидатов. Для FNV-1a-64 используются начальное значение `0xcbf29ce484222325` и множитель `0x100000001b3` с арифметикой по модулю 2^64.

```python
def fnv1a64(data):
    h = 0xcbf29ce484222325
    for byte in data:
        h = ((h ^ byte) * 0x100000001b3) & ((1 << 64) - 1)
    return h

ids = [token_id for word, token_id in candidates]
context = fnv1a64(
    (sentence + '\t' + ','.join(map(str, ids))).encode('utf-8')
)
```

В полном решении нужный участок `solar.exe` выполнялся в Unicorn с подготовленными объектами Haskell и заглушками функций среды исполнения. Поэтому способ решения сочетает разбор бинарника и адресную эмуляцию его функций.

Для данного бинарника использовались следующие виртуальные адреса при базе образа `0x140000000`:

| Адрес | Роль |
| - | - |
| `0x1400b4900` | Вход в функцию перестановки |
| `0x140132cc0` | Перехват записи кандидата |
| `0x140001f90` | Перехват очистки слота виртуальной машины |

На вход передаются упакованный `Word64` с ключом контекста, Haskell-список восьми идентификаторов и нулевой буфер состояния размером 256 байт. По записям и очистке слотов восстанавливается перестановка.

Внутри машины физический номер слота связан с логическим индексом `i` так:

```python
physical = (
    ((context >> 10) & 7)
    + i * (((context >> 7) & 7) | 1)
) & 7
```

Множитель всегда нечётный, поэтому соответствие на восьми слотах взаимно однозначное. Обратное отображение находится перебором `i` от 0 до 7.

Получив перестановку, находим в ней слово из PDF. Его индекс от 0 до 7 кодирует три бита, старшим битом вперёд. Например, индекс 5 даёт `101`.

# Формат скрытого сообщения

107 носителей дают 321 бит. Первые 320 бит составляют 40 байт кадра, последний бит — нулевое дополнение.

| Смещение | Размер | Содержимое |
| - | - | - |
| `0x00` | 2 байта | Длина полезной нагрузки, big-endian |
| `0x02` | 34 байта | Флаг |
| `0x24` | 4 байта | CRC32 полезной нагрузки, big-endian |

Восстановленный кадр в hex:

```text
0022534f4c41524354467b73306c34725f347261795f647333635f72337333347263687dcd9ca3d2
```

Начало `00 22` задаёт длину 34. CRC32 флага равна `cd9ca3d2`. Дополнительно проверяются точное число символов и нулевое дополнение.

# Почему потребовались два варианта вычислений

Квантованная ONNX-модель оказалась чувствительна к используемым вычислительным ядрам. На машине решения обычный запуск и запуск с AVX2 без AVX-512/VNNI иногда давали разный порядок кандидатов.

Здесь это влияет сразу на два этапа: меняется список кандидатов, а затем меняются строка для FNV и перестановка. Поэтому небольшое численное отличие может изменить декодируемый символ.

С ONNX Runtime 1.23.2 были получены такие результаты:

| Режим | Полезная нагрузка | CRC, записанная в кадре |
| - | - | - |
| Обычный запуск | `SOLARCTF{s0l4r_4ray_ds3c_r3s34rch}` | `cd8ca3d2` |
| AVX2 | `SOLARCTE{s0l4r[4ray_ds3c_r1s34rch}` | `cd9ca3d2` |

Ни один целый результат сам по себе не проходил проверку. Два набора отличались в четырёх трёхбитных символах. Если для каждой такой позиции взять оба наблюдавшихся значения, получается всего 2^4 = 16 сочетаний.

Ровно одно сочетание проходит длину, дополнение и CRC32 и даёт флаг, указанный в начале. Буквы не исправлялись вручную по смыслу: перебирались только значения, реально полученные в двух вычислениях. В исходном решении восстановленные символы также были переданы оригинальному декодеру кадра, который вернул успешный результат.

Воспроизведение двух режимов рассчитано на Linux x86_64. `cpumask.c` ограничивает сообщаемые возможности CPU внутри отдельного дочернего процесса. На другой архитектуре или другом процессоре доступные вычислительные пути могут отличаться; проверка уже сохранённых наблюдений от этого не зависит.

# Как воспроизвести решение

Исходные файлы: [the_last_case.zip](library-file\:libfile_4347bbf3a42481919d046dfc21de7eaf).

Пакет решения: [the_last_case_solution.zip](library-file\:libfile_ba6dc2c5b7448191abbff9657b7f2b29).

После распаковки пакета перейти в каталог со скриптами. Чтобы проверить сохранённые наблюдения, достаточно стандартного Python:

```bash
python solve.py
```

Ожидаемый вывод:

```text
SOLARCTF{s0l4r_4ray_ds3c_r3s34rch}
Length: 34; CRC32: cd9ca3d2
Checked 16 numerical variants; one valid frame.
```

Для повторного вычисления кандидатов и перестановок нужны исходный архив, Linux x86_64, `gcc` и зависимости:

```bash
python -m pip install -r requirements.txt
python solve.py --recompute /path/to/the_last_case.zip
```

Этот режим заново распаковывает ресурсы, вычисляет предсказания модели в двух режимах, эмулирует функцию перестановки и ищет единственный корректный кадр. Предложения и позиции масок берутся из сохранённой разметки `observations.json`.

| Файл решения | Что делает |
| - | - |
| `solve.py` | Распаковка ресурсов, вычисление вариантов, проверка кадра |
| `predictor.py` | WordPiece и запуск ONNX-модели |
| `vm.py` | Подготовка среды Haskell и эмуляция перестановки |

Основные места, где решение легко сломать: порядок текста в PDF, границы предложений, пробелы после переноса строк, отдельный токен `_`, удаление дубликатов без учёта регистра и порядок кандидатов при разных вычислительных ядрах. Проверка CRC32 позволяет отличить правильную сборку от внешне правдоподобного текста.
