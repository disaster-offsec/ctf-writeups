## 0. TL;DR цепочки

1. Три звонка с внешнего транка `svc-trunk@198.51.100.66` на добавочный **108**.
2. Код активации передан **двумя разными DTMF-каналами**: RFC2833 (`telephone-event`) и **тонами внутри аудио G.711**. В третьем звонке каналы чередуются группами по 4 цифры.

5. Склейка трёх чанков даёт контейнер `SOLPBK01`: PBKDF2-HMAC-SHA256(96-символьный код, salt, 60000) → AES-256-CTR.
6. Внутри — полный конфиг АТС с флагом.

## 2. Первый слой DTMF — RFC2833

```bash
tshark -r pbx_capture.pcapng -Y rtpevent -T fields -e frame.time_relative \
  -e rtp.ssrc -e rtpevent.event_id -e rtp.timestamp > dtmf.txt
```

Дедупликация событий по `rtp.timestamp` (каждая цифра = 3–4 пакета с одинаковой меткой):

```python
MAP = {10:'*', 11:'#', 12:'A', 13:'B', 14:'C', 15:'D'}   # раскладка DTMF
```

| SSRC | Звонок | Цифры |
|---|---|---|
| `0x1a46440f` | 1 (180–222 с) | `98B599B2CD56AC546B3CAD516DA618BA` (32) |
| `0x2ab0a429` | 105→101 (225 с) | `105` — обманка |
| `0x6c606b40` | 3 (650–692 с) | `899C90A0437BC9560C` (18) |

Во втором звонке (453–495 с) RFC2833 **нет вообще**.

Два наблюдения, которые задают направление:

* алфавит кодов — ровно `0123456789ABCD` (события 10/11, т.е. `*` и `#`, не встречаются ни разу) — значит, генератор брал 14-символьный «телефонный» алфавит;
* в третьем звонке цифры идут группами по 4 с паузой 1.78 с между группами, хотя внутри группы шаг ровно 0.58 с. **В паузах что-то происходит.**

Перебор PBKDF2/AES со всеми вариантами этих кодов ничего не даёт — значит, код неполный.

Шестёрка «настоящих» потоков — это три пары разговоров: звонок 2 (453 с), звонок 3 (650 с) и внутренний 115→116 (855 с). Декодируем A-law в PCM и прогоняем алгоритм Гёрцеля по восьми частотам DTMF:

```python
def alaw2lin(a):
    a ^= 0x55; t = (a & 0x0f) << 4; seg = (a & 0x70) >> 4
    if   seg == 0: t += 8
    elif seg == 1: t += 0x108
    else:          t = (t + 0x108) << (seg - 1)
    return t if (a & 0x80) else -t

KEYS = [['1','2','3','A'], ['4','5','6','B'], ['7','8','9','C'], ['*','0','#','D']]
```

Сегментация по RMS (тон 0.2 с, пауза 0.1 с), отношение энергии победителя к второму месту — **377×+**, т.е. декод однозначный:

## 7. Формат контейнера

```
offset  size  поле
0       8     "SOLPBK01"
8       1     version = 2
9       4     PBKDF2 iterations = 60000      (LE32)
13      16    salt = e2747bc64c9ca2a9cc41e90c4db311bf
29      16    iv   = 5102a27ebab521b46f308bbc914c7195
45      4     ciphertext length = 1811       (LE32)
49      4     reserved = 00000000
53      4     crc32(plaintext) = 9e34e966    (LE32)
57      1811  ciphertext
```

Длина 1811 (не кратна 16) → потоковый режим. Схема подтверждается самим конфигом: `kdf = pbkdf2-hmac-sha256`, `cipher = aes-256-ctr`.

> Подводный камень: контейнер одинаково хорошо «читается» и при раскладке `… len | reserved | ct(1811) | crc`, и при `… len | reserved | crc | ct(1811)` — обе дают ct = 1811. Верна вторая. Проще всего перебрать оба варианта.

## 8. Расшифровка

```python
import hashlib, struct, zlib
from cryptography.hazmat.primitives.ciphers import Cipher, algorithms, modes

d = open('pbx_backup.solpbk','rb').read()
iters = struct.unpack('<I', d[9:13])[0]
salt, iv = d[13:29], d[29:45]
crc = struct.unpack('<I', d[53:57])[0]
ct  = d[57:]

PW = ('98B599B2CD56AC546B3CAD516DA618BA'
      '566CBC4A0D591732CD5AB9794C381A'
      '899C016A90A0A331437BC950C9569C380C')

key = hashlib.pbkdf2_hmac('sha256', PW.encode(), salt, iters, 32)
pt  = Cipher(algorithms.AES(key), modes.CTR(iv)).decryptor().update(ct)

assert zlib.crc32(pt) & 0xffffffff == crc     # 9e34e966 — сходится
open('pbx_backup.conf','wb').write(pt)
```

## 11. Чему учит задача

* **Один звонок — не один DTMF-канал.** Wireshark показывает только RFC2833; тоны в полезной нагрузке надо искать самому (Goertzel / спектрограмма). Статистика уникальных значений сэмплов — дешёвый способ найти «живые» потоки среди шума.
* **Паузы в потоке цифр — это сигнал.** Регулярный шаг 0.58 с и разрывы 1.78 с ровно через 4 цифры — прямой намёк на второй канал.
* **Перехлёст фрагментов.** Совпадение `…BA`/`BA…` и `…89`/`89…` — маркер сшивки, а не мусор; без него полный ключ не собрать.
* **Эксфильтрация может быть «размазана» по протоколам.** Детект по одному каналу (например, только SMTP) пропустил бы 2/3 файла.
